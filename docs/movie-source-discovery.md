# 影视接口发现、换源与网页接力

## reader.13 查询范围和作品类型

`sources.json` 中的基础配置入口、发现页面、展开后保存的兼容目录，以及某次查询实际访问的目录，分别统计。工具从当前资产读取入口数量，从当前注册表和目录客户端读取兼容目录数量，不把首批目录数或网页候选数当作已配置来源总数，也不把配置条目数当作可播放来源数。

`video_search` 的 `source_inventory` 返回 `bundled_config_roots`、`bundled_discovery_pages`、`built_in_catalogs`、`registered_catalogs`、`eligible_catalogs`；有本次查询报告时还返回去重后的 `queried_catalogs`、`successful_catalogs` 和 `remaining_catalogs`。成功查询只表示返回了可识别目录数据。各失败阶段继续保留自己的 `total`（选定分组）、`eligible`（客户端整个兼容目录池）、`attempted` 和 `unqueried`，不混用分组范围和全部来源范围。成功返回播放器时也保留本次范围。

明确年份的请求逐个处理目录返回的结果，某个来源验证成功即可返回播放器并取消其余请求；先到来源的媒体失败后仍尝试后续来源。没有年份时保留同名不同年份的歧义检查。现有并发、单请求、单来源和整轮时限继续生效；配置入口仍须经过发现与格式筛选，未承诺每轮访问完所有入口。

`video_search` 和 `video_resolve` 接受可选 `content_type`：`anime`、`film`、`series`、`general_video`。类型随这次请求传到目录和网页回退，用户纠正为动漫后应重新按动漫请求。动漫查询优先具体集数，第一集也需真实分集信息；解说、讲解、混剪和预告不能作为正片。目录的明显真人剧分类与动漫请求冲突时跳过，媒体提取器返回的解说标题也在被目录标题覆盖前排除。短篇动画和剧集不使用电影的十分钟阈值。

未知类型元数据仍返回 `content_type_verified=false`，成功解析也保留 `full_length_verified=false`。类型匹配和媒体可解析均不能证明整片已观看或每一帧可用。`video_find_sources` 的返回数量仅是当前网页查询的有限候选数量，其 `scope=webpage_candidates`、`is_catalog_inventory=false`，不能据此汇报来源总数。

播放器读取并保留 `requested_content_type`；换源选项、当前选中的目录、刷新及自动恢复继续传递同一类型。换源缓存和选项 ID 按类型隔离，泛视频缓存不能混入动漫换源列表。手动换源也会重新检查作品分类及媒体提取器的标题，不能在刷新后将解说标题覆盖成正片标题。

来源统计同时保留每个阶段实际看到的兼容目录 ID。追加发现后按 ID 合并查询覆盖；注册表达到上限、旧目录被淘汰时，`eligible_catalogs`、`queried_catalogs`、`remaining_catalogs` 对应当前目录池。`queried_catalogs_across_stages`、`eligible_catalogs_seen_across_stages` 另保留本次所有阶段的历史覆盖，`retired_queried_catalogs` 表示本次查过但已经不在当前池中的目录，避免把历史 ID 膨胀成当前来源数。

本轮在已有聊天播放器和“换源”菜单中接入来源发现，不新增影视首页、来源管理页或其他常驻 UI。新增流程已完成构建与下文列出的运行检查；具体通过项及边界以本轮安装包旁的验收记录为准。

## 查找顺序

1. `video_search(title, year?, episode?)` 先检索原有无损云、暴风、豪华目录及已保存的兼容目录，核对片名、年份和分集后尝试真实媒体线路。
2. 现有目录不能取得对应影片时，扫描已知配置入口，展开单仓/多仓，只提取当前原生客户端能处理的独立 HTTP JSON/XML 接口，增量保存并尝试新增接口。配置读到 HTTP 200 不直接创建播放器。
3. 新发现接口搜索到同片、同年、同集的线路后，才能成为现有“换源”菜单中的候选。配置可读取、接口搜索命中、媒体解析成功和实际解码播放是分别检查的状态。
4. 目录阶段仍失败时，在同一次工具调用中用当前搜索服务找具体网页，检查真实页面，再解析候选视频。自动网页阶段最多两组不同查询、六个候选、四次页面读取、四次解析，总时限 90 秒；页内找到的播放链接也计入相同预算。
5. 程序内的有限候选仍失败时，把准确失败状态和已核对的网页候选交给模型。模型可通过 `video_find_sources` 自主更换关键词、原语言片名、年份或集数，再使用 `web_fetch`、`video_resolve`，不把目录中没有片源当作没有搜索能力。

片名存在明确同名年份歧义时返回 `ambiguous_title`，要求补充年份，不自动猜版本。预告、片段、解说、明确错年和错集结果不能冒充目标正片。网页解析后已知时长不足十分钟的候选不作为完整电影结果；片长未知时标明未知，能够解析某个媒体也不代表整片内容已核验。

## 配置发现来源

用户提供文件为 `影视接口功能_AI接入精简包.zip`，SHA-256：

```text
63f4497d7106c835de23cc2a657a71070fd42f972bfde9831101b596ca2e7c69
```

包内 `sources.json` 包含 57 条基础线路、20 个发现页面；Java `ConfigDecoder` 和 `ConfigDiscovery` 是配置读取参考核心，不是影片搜索引擎或播放引擎。来源地址未因被打包就被认定为当前可用。

应用保留该来源清单及出处记录，扫描在后台执行：六个工作协程、整轮最多 35 秒，每个根配置最多 15 秒，根深度为 0、最多展开到 3 层，每仓最多八个子配置、每根最多 24 节点。每轮最多读取四个发现页面。最近成功配置、HTTPS 和可直接读取的仓库配置优先；新从页面发现的地址安排在首批优先根之后，避免一直排在旧地址末尾。取消会停止当前网络请求及后续扫描，已完整发现并保存的接口可保留。

核心支持包中已有的普通/嵌套 JSON、Base64、gzip 和自描述配置容器解码。只把解码后的配置当数据使用，不下载或执行配置中的 spider、JAR、JavaScript 规则，不将远程脚本作为播放器插件安装。因而只有插件引用、没有独立兼容 HTTP JSON/XML API 的配置，不能直接成为原生目录。

新增来源使用 `discovered_` 加 API 地址摘要作为稳定 ID，私有注册表最多保存 128 项，近期发现优先。成功扫描缓存六小时，无兼容接口的扫描缓存五分钟；支持内部强制重试。单次目录查询仍有候选数量、网络并发和时限预算，保存 128 项并不意味着一次同时访问全部接口。

配置下载与动态接口读取复用应用网络客户端和代理，保留标准证书校验，逐次检查地址、DNS 和跳转；不附加应用其他账户的登录凭据。注册表只保存目录定位数据，不保存影片文件、聊天记录或可执行插件。接口字段、目录名称和网页内容都是不可信数据，不能作为模型指令。

## 播放失败与手动换源

换源菜单使用增量查询：已有缓存或当前来源的真实线路先显示，每个目录返回后补充列表，不再等待整批结束。现有目录查询与配置发现同时开始，发现的新兼容接口继续参与查询；关闭菜单会取消这轮未完成请求，已完整取得的匹配结果保留在缓存中。首次只有预览元数据、没有真实线路详情时，不伪造可选线路。

目录查询不再固定截取前 15 个来源。每个客户端共享六个查询名额，每次 HTTP 最多八秒，单来源的搜索及详情两阶段合计最多十六秒，单轮最多二十四秒；优先近期响应的目录，其余队列轮转，重试时后续来源有机会先查询。配置发现最多三十五秒，新加入目录的补充批次最多十六秒，列表在此期间持续可选。慢源不会阻止快源先显示，实际总数仍由同片、同年、同集的真实命中决定。

缓存随已注册目录集合变化失效；并行快照合并仍核对片名、年份、集数，不能把旧缓存中的错年影片重新并入。自动换源等待增量流中的后续候选，不因首批只有当前失效来源就提前通知 AI 接手。

有目录定位的播放器初次解析失败，或媒体实际载入/解码失败时，自动跳过当前失败线路并尝试其他候选。每个播放器的一轮自动切换最多六条、总预算 120 秒；单条解析最多 20 秒，载入后等待原生播放器就绪最多 15 秒。相同失败项不循环重试，正常播放或暂停不触发自动换源。

手动“换源”继续可用，不因自动预算耗尽就禁止用户选择列表中的其他项。手动选择先解析新线路，解析失败保留原来仍可用的媒体；新媒体实际载入后再次失败，才能继续自动寻找其他线路。切换继续复用现有播放器，并保留当时进度、倍速、播放/暂停意图和全屏状态。

清晰度菜单显示当前媒体真实提供且设备支持的轨道。低清单档源可手动换其他来源；不会因为目录写着“4K”就把真实低清轨道标成 4K。必要留边、源文件自带黑边和已被片源本身截掉的字幕也不由接口发现功能修复。

播放器穷尽自动候选后，可以把失败交回当前聊天的模型继续自主查找。恢复限定于当前分支最后一个用户回合，并且每个用户回合最多自动接手一次，以避免新播放器失败后产生无休止的模型和搜索请求。续跑使用当次运行的提示，不伪造用户消息、不覆盖原聊天记录，也不绕过已有工具审批；用户停止、切换会话或状态不再匹配时不得抢占继续执行。

## 搜索服务与解析边界

网页接力和 `video_find_sources` 使用设置中当前选中的搜索服务，独立于普通网页搜索开关，也不依赖模型是否内置搜索工具。默认 Bing 请求已改为使用注入的 OkHttp 客户端及代理，解析真实搜索结果地址；搜索服务不可用、验证码或无结果会准确报错。不会静默轮换用户配置的其他付费搜索服务。调用当前所选搜索服务和模型仍可能按其正常规则计费。

`video_resolve` 先处理可识别 MP4/HLS/DASH 直链。普通视频网页会读取实际 `<video>`、媒体属性和结构化数据中的地址，再按需要使用既有增强提取器；不会猜测不存在的 URL。真实播放地址、请求头及签名尽量留在本地播放缓存，模型读取的是原页面和本地预览标识。

网页可访问、媒体头检查成功、播放器就绪和短段实际播放都不能证明整片可用。登录、会员、地域、格式、DRM、验证码和第三方服务变化仍可能使来源无法播放；本轮没有新增这些限制的绕过算法。所有方法耗尽后应报告当前未找到可验证来源，不保证每部电影都有可播放或高清版本。


## 目录格式和失败状态（2026-11-02）

普通影视目录同时识别 JSON 与 MacCMS XML，包括 XML 列表、CDATA、详情、多线路和多集播放信息。
只按响应实际结构解析，不以服务器误写的 Content-Type 决定可读性；XML 不允许 DTD、外部实体或外部网络解析。
真实的空 list 才是有效空目录；缺少 list、错误对象、不可识别结构和非空但完全无法识别的记录列表都作为失败来源统计。

每次查询独立保留已尝试、成功、有效空目录、失败、超时和未查询数量，不使用跨聊天共享的最近一次状态。
`video_search` 的失败结果带 `catalog_status` 和 `catalog_stages`：`no_match` 只表示本次已完成查询的目录无匹配，
`partial_search` 表示部分失败或未完成，`sources_unavailable` 表示没有来源成功返回有效数据，
`playback_failed` 表示已找到对应条目但线路验证失败。诊断仅输出计数、固定错误码和安全来源 ID，不传远端原始错误文本。
现有接口发现、网页接力、成功播放器结果以及取消流程继续保留。

此修复补齐 XML 兼容和错误分类，不保证任意指定新片一定已有可用片源。实际验收结果以本次 outputs 中的记录为准。

## 本轮验证（2026-10-30）

- Android 实际 `org.json` 下运行原包离线断言，核对 57/20 来源资产、嵌套配置、防环、缓存、取消及新发现优先级。
- 动态注册后复用同一个目录客户端搜索影片，确认无匹配影片的配置不会出现在换源列表；从新增来源选择后验证原生解码和实际进度。
- 初次解析失败、真实媒体 404/解码失败后自动替换，核对次数上限、同播放器状态保留和最终失败出口。
- 原目录成功时不启动后续阶段；同名歧义和取消立即停止；网页候选成功进入已有聊天播放器缓存，错误及模型结果不泄漏签名或请求头。
- 当前会话所有来源失败后，验证只接手一次的模型续跑、原记录保留、取消/停止/新消息与审批状态处理。

已完成 145 项 JVM 检查：38 项电影目录/发现/网页接力、88 项视频/网页读取/工具/恢复策略、6 项 Bing 网络解析和取消、13 项会话服务回归，全部通过。

Android 本地验证共 27 项不同测试通过，包含原包 46 条离线断言在系统 `org.json` 上运行、配置递归和取消、动态目录命中后出现在现有菜单并真实解码、新增网页接力真实解码、404 后自动换源及播放器/进度/倍速/全屏保留、最终失败通知只触发一次、两次模拟 `/v1/chat/completions` 请求中的临时恢复提示与新回答追加，以及原有 13 项控件/字幕/播放回归。首次网页测试误把现有的 `GET Range: bytes=0-0` 验证方式写成 HEAD 断言，修正测试后重新验证两项网页测试通过；没有为迁就断言改生产网络方法。

真实联网扫描本包默认入口约 35.3 秒，收集到 128 个兼容 HTTP API 定义，达到本地注册数量上限。该数字只表示可读取配置中解析出的接口定义，不能称为 128 个已验证可播片源；真实搜索命中和实际播放分别验证。另复测《惊天魔盗团3》(2025)搜索、短段实际播放及全屏往返通过，使用 wsyzy/130439，实测视频 1920×800、时长 6,799,113 ms。两项联网测试与 27 项本地 Android 测试合计 29 项。测试只使用独立模拟器及原创测试视频，没有调用用户付费模型或搜索接口，也未修改手机聊天数据；没有观看整片。优化构建、签名、非调试标记及模拟器冷启动检查通过，最终交付检查以 APK 旁的本轮验收 JSON 为准。
